# Protocol components and reusable acquisition templates

Target version: 1.0.3
Created: 2026-09-09

## Scope and intent

Provide a maintainable first delivery of TCP, UDP, HTTP, Modbus-TCP, OPC UA and Siemens S7 acquisition templates that send normalized values through the existing ThingLinks uplink. ONVIF, GB28181 and native cloud MQTT/WebSocket access are outside this task. Modbus-RTU remains unavailable until controlled serial device access exists; CoAP, BACnet and IEC104 remain explicit extension candidates rather than executable placeholder templates.

Implementation, local commits and deployment follow the user's current authorization. Preserve concurrent work and require explicit scope for pushes or changes to existing running instances; isolated tests must use captured task-owned resources.

## Layers and ownership

- `core/protocols/`: protocol catalogue, exact driver requirements and readiness evaluation. Reuse existing package approval, store and instance installation services.
- `core/flows/templates/`: declarative parameters, bounded validation and a catalogue of built-in recipes; `builtin/` holds one protocol per file. Builders are pure functions producing Node-RED flows; they cannot install modules or touch an instance.
- `core/flows/`: existing persistence plus metadata, reference-safe append and deployment preflight. HTTP handlers only authenticate, validate and delegate.
- `http/protocols/`: read-only component catalogue/readiness routes. Installation uses the existing node installation API and its authorization/operation gate.
- `views/flows/components/`: filtering, parameter forms and deploy preview. API/state remains outside presentational form components.
- `scripts/`: pinned protocol seed generation and offline package integration, preserving upstream package integrity and dependency closure.

## Template contract

Existing template fields remain supported. Add optional `origin` (`builtin` or `custom`), `category`, `protocols`, `revision`, `requirements`, `parameters`, and `notes`. Existing custom templates default to category `custom`; origin is server controlled. Categories are `industrial`, `network`, `building`, `power`, `custom`. Protocols are independent tags, so one user template may cover multiple protocols.

Built-in IDs begin with `builtin:`. They are immutable and versioned; users render a configured copy into an ordinary custom template. Package requirements contain `module`, exact `version`, and `nodeTypes`. Parameter fields contain key, label, type (text/number/select/boolean/table), required/default/description/bounds/options; table columns use the same scalar fields. No interpolation of executable user code. Reject unknown/unsafe object keys, invalid field types, out-of-bounds values and excessively large tables.

GET `/api/templates` includes builtin metadata and custom records. GET `/api/templates/:tid` exposes disabled example flows for builtin recipes. POST `/api/templates/:tid/render` with `{parameters}` returns `{template}` for a validated configured copy. POST/PATCH custom templates support category and protocol tags. Builtin PATCH/DELETE are refused.

POST `/api/instances/:id/flows` adds `mode` (`append` or `replace`) and `parameters`. The UI and builtin recipes default to append; omission on legacy custom/direct flow calls retains replace for API compatibility. Append remaps flow/config/subflow references, retains existing flows and uses revision-aware Node-RED writes to detect editor changes. Preflight must fail closed for builtin dependencies when installed types/versions cannot be confirmed; it must reject missing/disabled nodes or incompatible exact driver versions. Dry-run describes the result without writing. Deployment rechecks under the instance operation gate. External device traffic, actual read permissions and ThingLinks registration/model matching remain separate runtime gates.

## Acquisition behavior

Templates declare the device and use `tl-uplink` with an explicit nodeId and serviceCode. Point mappings normalize values into cloud property codes. Field parameters include endpoint/port, timing and relevant address or variable tables. Invalid frames/values report through Node-RED catch/status rather than emitting plausible data. No real addresses, credentials or unbounded polling defaults are embedded. Examples are disabled until configured and deployed. TCP provides explicit framing; UDP handles independent messages; HTTP includes polling and receive scenarios with their network prerequisites documented. Modbus decoding covers common register types/byte order; OPC UA and S7 expose variable-to-property mappings.

## Component distribution

Built-in Node-RED networking nodes need no additional packages. Third-party Modbus, OPC UA and S7 versions are pinned using current published metadata; package presence, approval, installed version and runtime loading are distinct statuses. Protocol packages are distributed through the existing seed/offline machinery. Installation is explicit and does not silently restart existing instances or change their approval policy. Credentials stay in instance configuration and never enter shared templates.

## Acceptance

1. Category/protocol metadata survives create/update/read and existing rows remain readable.
2. Every first-batch recipe renders a valid flow from checked parameters, supports multiple point mappings where applicable, and produces the existing uplink contract.
3. Append preserves existing nodes, remaps internal references and rejects stale deployments. Builtin dependencies are checked before a write.
4. UI filters and forms work with existing custom templates and show actionable missing-component or configuration feedback.
5. Fixed protocol seeds preserve integrity and closure; real isolated Node-RED validation covers installation/loading and sample acquisition, without restarting or modifying existing instances.
6. `pnpm check` and `pnpm build` pass. Browser and container outcomes are recorded separately from real hardware/cloud acceptance.

## Approved refinement: model-assisted bidirectional operation

The user subsequently required the standard ThingLinks MQTT contract for both telemetry and commands, based on current Cloud source, and a product-oriented configuration experience. This extends the acquisition implementation; it does not replace it.

- Configuration groups: device/connection, cloud model, points, optional commands and advanced settings. Topic construction and the `head/dataBody/dataSign` envelope remain internal.
- Model assistance queries the explicit child product identification and bound version through MQTT `model/query`. Service/property/command selectors display names with their codes. Known mismatches block use; unsynchronized models are explicitly unverified and never silently use the gateway model.
- Downlink uses `/v1/devices/{gateway}/command`; body fields are `deviceIdentification`, `serviceCode`, `cmd`, `params`, with optional product/version context. Edge routes only explicit device/service/command bindings. Mapped writes are opt-in and bounded; driver acknowledgements or verified responses determine execution status.
- Replies use `/v1/devices/{gateway}/commandResponse`, the received `head.mid`, and `{deviceIdentification,msgType:'deviceRsp',serviceCode,cmd,errCode,params,errMsg}`. Unknown targets, invalid parameters, timeouts and ambiguous ownership never execute optimistically.
- The bridge persists deduplication/results, uses a single delivery lease without automatic actuator replay, expires stale consumer bindings and retries replies independently of device execution. Node-RED templates consume an instance-authenticated Manager bridge using ordinary HTTP nodes; the published platform package is not silently patched.
- Current Cloud stores a separate response under the topic device, without matching/updating the original command by `mid`. It retains child encryption/transport settings when routing to the gateway. These source-confirmed Cloud boundaries cannot be represented as solved by an Edge acknowledgement.

Design references (read 2026-09-09): [ThingLinks envelope](https://mqttsnet.yuque.com/trgbro/thinglinks/cbswp2a9y7tppkar), [ThingsBoard connector forms and request mapping](https://thingsboard.io/docs/iot-gateway/config/modbus/), [NeuronEX device/group/tag workflow](https://docs.emqx.com/en/neuronex/latest/configuration/groups-tags/groups-tags.html). These inform usability; current ThingLinks source determines wire contracts.

## Acceptance refinement: child device status synchronization

The user's end-to-end requirement includes truthful cloud device state. The data and state channels are separate: current Cloud `datas` persists values, while `topo/update` changes a child's connection state and last status-report time. A data publish acknowledgement cannot prove either persistence or status synchronization.

- Keep status coordination in `core/cloud/presence/`, separate from telemetry batching, historical replay and command execution. HTTP ingestion supplies authenticated, successfully validated live observations; it must not await cloud state work or lose telemetry because state synchronization failed.
- Discover candidates from actual live child uplinks, never by replaying the entire historical field-device table. Exclude the gateway itself. Use official `topo/query` for explicit candidate IDs, accepting only successful per-device records with `nodeType=2` and `gatewayId` matching the current gateway. Current Cloud status-update handling does not enforce that ownership itself; this client check is required here and does not claim to repair server-side authorization.
- Coalesce state changes and bound work, batches and retry frequency. Send at most 100 devices in a batch. A successful top-level status code is insufficient: match every requested device to exactly one successful result, preserve failed or absent items for bounded retry, and expose failures through existing diagnostics.
- State publication must not leave stale ONLINE packets in the MQTT client's automatic reconnect queue. Use a non-replaying transport for status requests while retaining application-level response confirmation and current-state retries; telemetry and command-reply QoS contracts remain independent.
- Live data establishes ONLINE. Explicit offline reports and confirmed instance stop/removal establish OFFLINE. Failure to inspect Docker is unknown, not stopped. Do not invent an idle timeout for event-driven devices; silence and malformed readings alone do not prove transport disconnection.
- Repeated ONLINE refreshes require a newer live observation than the last confirmed report. An old in-memory ONLINE flag is not permission to manufacture fresh cloud heartbeat times; reconnect also needs current live evidence before restoring ONLINE.
- Persist only the minimum state of observed candidates needed to reconcile restart. After Manager restart, a running instance must supply new live data before ONLINE is restored. Historical spool replay never makes a device online. On cloud reconnect, validate ownership again; on gateway configuration change, keep old-gateway observations from leaking into the new gateway.
- Serialize synchronization, isolate late asynchronous replies by connection/observation generation, and handle multiple instance sources conservatively so one stopped source cannot overwrite another live source. Shutdown must stop timers and bound outstanding work.

Acceptance adds live-data ONLINE, confirmed-stop OFFLINE, stop/start recovery, reconnect reconciliation, foreign-device rejection, partial-result handling and no status resurrection from historical replay. Hardware-specific disconnect detection and configurable inactivity policies remain separate capabilities and must not be represented as delivered by this refinement.

## Approved refinement: reuse Node-RED protocol execution

- Protocol transport and device read/write belong to existing Node-RED nodes. Edge supplies parameterized recipes, model mapping, deployment checks and the standard ThingLinks uplink/downlink bridge. Retired custom OPC UA executors must not remain in the production source tree.
- The compatibility OPC UA recipe remains collection-only. The separate secure recipe uses the published `@tier0/opcua-client` package and explicit certificate references; package bytes, dependency closure and matching native platform artifacts are distinct preparation gates.
- Current catalogue capability restrictions must be enforced in parameter generation and explained for saved snapshots. Saved user content is not silently changed; an older snapshot cannot be described as repaired merely because its current builtin source has disabled control.
- A command result may be unknown after the device has already acted. The bridge guarantees no automatic re-dispatch, not cancellation of bytes already handed to a driver. A driver whose failed request can execute after recovery must not be advertised as having passed that control boundary.
- Real protocol servers and virtual TTY pairs can verify transport behavior. They do not establish physical PLC, USB/RS485, firmware or all-model compatibility. Test registries mount only required public source paths and package archives, never the full checkout or local credentials.
