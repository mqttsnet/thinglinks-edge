# Node-RED Published Package Migration Design

**Target version:** `1.0.2`
**Created:** 2026-09-01
**Status:** Confirmed for implementation planning
**Owner:** ThingLinks Edge
**Related package repository:** `mqttsnet/thinglinks-node-red`
**Implementation plan:** [v1.0.2 Node-RED published package migration](../plans/v1.0.2-node-red-published-package-migration.md)

## Context

ThingLinks Edge currently ships seven raw Node-RED files inside the Manager image, copies them into every instance under `/data/nodes`, and lets Node-RED load three types from that directory:

- `tl-device`
- `tl-tag`
- `tl-uplink`

The same implementation is now published as independently versioned npm packages:

- `@mqttsnet/thinglinks-edge-nodes@0.0.1`
- `@mqttsnet/thinglinks-node-red-common@0.0.1`

The Edge package is public, has been added to the Node-RED Flow Library, and has passed a real `nodered/node-red:5.0.4-24-minimal` installation and runtime matrix. The local Edge Manager npm proxy can resolve, cache, and serve both published tarballs.

The current Edge product path is not ready to consume the package without migration. The old raw files and the npm package register the same three node types. Node-RED can return HTTP 200 from `POST /nodes` while marking the npm node sets with `type_already_registered`, so install success alone is not proof that the npm implementation is running.

## Official discovery boundary

Three distinct discovery layers must remain explicit:

1. **npm registry:** authoritative source for package installation and version metadata.
2. **Node-RED Flow Library:** public community listing. The Edge package has been manually submitted and is searchable there.
3. **Node-RED Community catalogue:** the static catalogue used by Palette Manager. It updates independently from the Flow Library and may lag after a new submission.

The Edge console must not depend on Flow Library or Community catalogue refresh timing. Exact package lookup and fuzzy npm search are handled through configured npm sources. The local ThingLinks catalogue remains useful for approved, version-pinned, and offline packages.

## Goals

- Make exact and fuzzy Edge node searches return the published Edge package reliably.
- Make all newly created instances use the npm package instead of raw copied files.
- Provide an explicit, observable, rollback-safe migration for existing instances.
- Preserve current flows, credentials, ports, image tag, resource limits, and original running/stopped state.
- Make module inventory distinguish healthy npm loading from raw, builtin, conflicting, and failed node sets.
- Keep common as a normal transitive dependency: it is never approved, allow-listed, or displayed as a Node-RED module.
- Preserve offline installation by seeding the exact published Edge/common tarballs into the Manager package store.
- Prove installation, startup loading, Manager reporting, allowList removal, and recovery with the real Node-RED 5.0.4 image.

## Non-goals

- Do not publish another npm version as part of this migration.
- Do not submit common or Cloud packages to the Node-RED Flow Library.
- Do not migrate `line-1` before the isolated migration and rollback matrix is green.
- Do not delete legacy raw files during the first migration release.
- Do not classify every package under `@mqttsnet` as a ThingLinks platform package.
- Do not make Manager reporting failure a reason to roll back an otherwise healthy module load.

## Fixed package contract

The first migration release uses these immutable values:

```text
Edge package:      @mqttsnet/thinglinks-edge-nodes@0.0.1
Edge integrity:    sha512-NKsIKyUHNyB+xuXNpCrOqzEYbYflEFeXqC/IgjM2/+AzktSTb7+TZFBWHoqp9FjLDX2crpoah6gn8n+Uy32AkA==
Common package:    @mqttsnet/thinglinks-node-red-common@0.0.1
Common integrity:  sha512-T6QN9RlBF0qbvujaAKNY81BjrcIdbqeqFkLfQsGuKHI8UY2cgad9prF8xUC5n4BbHbNJ7ftBmSBkj+IEZvTJWQ==
Node-RED image:    nodered/node-red:5.0.4-24-minimal
Node types:        tl-device, tl-tag, tl-uplink
```

A dedicated `platform-package.ts` owns these constants. Callers do not duplicate package names, versions, integrities, or type lists.

## Selected approach

Use a staged compatibility migration:

```text
legacy raw active
  -> preflight
  -> npm package staged while raw remains active
  -> npm-mode settings exclude three raw runtime files
  -> one restart
  -> verify npm ownership and flow health
  -> commit runtime mode
```

Legacy files remain on disk as rollback assets. The migration does not rename or delete `/data/nodes`.

Node-RED 5.0.4 always scans `<userDir>/nodes`, so removing `settings.nodesDir` alone does not disable the old files. In npm mode, generated settings add these basenames to `nodesExcludes`:

```text
tl-device.js
tl-tag.js
tl-uplink.js
```

Node-RED applies these exclusions to raw files under `/data/nodes`; it does not apply the same basenames to files declared inside an npm package's `node-red.nodes` metadata. This suppresses raw registration while allowing the scoped package to load.

## Persistent instance model

Database migration v13 adds instance-level runtime state plus a durable migration journal. Existing rows default to the current behavior.

```text
node_runtime_mode     legacy | npm             default legacy
platform_node_version text                     default empty
node_migration_state  idle | preparing | checkpointed | staged | cutover |
                      verifying | pending_start_verification |
                      rolling_back | committed | rolled_back |
                      rolled_back_dirty | manual_required
node_migration_error  text                     default empty
```

`instance_node_migration` stores the single current/last platform-node bootstrap or migration transaction per instance:

```text
instance_id       primary key and foreign key to instance
tx_id             generated opaque transaction id
operation_kind    bootstrap | migration
state             same migration-state union as the instance projection
original_running  boolean captured before runtime mutation
staged_before     boolean: exact Edge package already existed before migration
mode_before       persisted runtime mode before migration
image_id_before   inspected immutable image id used for exact rebuild/rollback
target_integrity  fixed Edge integrity for this transaction
checkpoint_dir    Manager-controlled path below
                  <instanceDataRoot>/.thinglinks-migration/<instance_id>/<tx_id>
snapshot_json     hashes and non-secret runtime evidence only
actor             authenticated actor id
started_at        transaction creation time
updated_at        last durable phase transition time
error             redacted failure summary
```

The journal foreign key cascades only when a later, normally permitted instance deletion removes the instance. `manual_required` blocks ordinary removal, so recovery evidence cannot be erased through the normal API before explicit repair/cleanup.

The journal is the recovery authority; the state/error columns on `instance` are a list/UI projection. Every phase update changes both in one SQLite transaction. Startup treats a projection/journal mismatch as inconsistent evidence and moves the instance to `manual_required` instead of guessing which side is newer.

For an existing-instance migration, before the first runtime side effect the Manager computes a read-only snapshot and inserts the `preparing` journal row in a database transaction. It then creates a mode `0700` partial checkpoint directory under the Manager-only sibling root `<instanceDataRoot>/.thinglinks-migration/<instanceId>/<txId>` (outside the live instance bind mount), copies `settings.js`, flows, credentials, `package.json`, lock files, and Node-RED module-state files with source-equivalent restrictive permissions, writes and fsyncs a manifest of their SHA-256 hashes, atomically renames the checkpoint into place, and persists `checkpointed`. The journal never stores credential bytes, ingest tokens, container environment values, or plaintext secrets. Recovery from migration `preparing` removes an incomplete partial checkpoint without touching live runtime state.

New-instance creation writes a `bootstrap/preparing` journal in the same transaction as its traceable instance row before creating data, network, or container resources. It has no prior checkpoint. Startup recovery compensates an interrupted bootstrap by verifying resource removal, then deletes the row only on clean compensation; any residual becomes `manual_required`.

Clean `committed` and `rolled_back` outcomes securely remove and verify the checkpoint after the terminal database transaction. `pending_start_verification`, `rolled_back_dirty`, and `manual_required` retain it for recovery/diagnosis. A terminal checkpoint cleanup error is redacted/audited and retried idempotently at startup; it never causes the Manager to print or copy secret-bearing files into logs.

Rules:

- Existing instances migrate to schema v13 as `legacy`.
- New instances are created as `npm`.
- `resetCredential`, `applyNodePolicy`, image upgrade, same-image rebuild, and restore all render settings from the persisted mode.
- A running instance sets `node_runtime_mode=npm` only with a fully verified `committed` transition. A stopped instance may set npm mode with `pending_start_verification` only after its exact protected data copy passes the full isolated runtime proof; its next explicit live start must verify before becoming committed.
- Failure keeps or restores `legacy`; a package cleanup failure results in `rolled_back_dirty`, not success.
- Each phase transition is durable before its corresponding runtime side effect.
- Manager startup constructs the migration dependencies, reconciles historical instance networks, and `await`s `recoverInterrupted()` before `app.listen()`. Interrupted bootstrap journals run verified creation compensation; interrupted migration `preparing/checkpointed/staged/cutover/verifying/rolling_back` journals roll back from their checkpoint; `pending_start_verification` remains stopped until an explicit start. A failed recovery becomes `manual_required`; the Manager may then listen for read-only diagnosis, but mutating operations for that instance remain blocked.

## Instance operation gate

Creation, migration, direct package installation, whole-flow replacement, start, stop, policy apply, credential reset, image upgrade, same-image rebuild, removal, and reverse-proxied editor writes/WebSocket upgrades share one per-instance operation gate. The gate is injected through the Manager HTTP context/unified service facade so HTTP routes cannot bypass it. The existing offline restore command runs while the Manager is stopped and is not a runtime-gate operation; any future online per-instance restore must use the gate.

While an instance is migrating:

- mutating Manager APIs for the same instance return a maintenance response;
- the Node-RED reverse proxy rejects editor writes, package changes, and new WebSocket upgrades while allowing read-only status; existing editor sockets are drained/closed before the first migration runtime side effect;
- a second migration request atomically observes and returns the existing migration transaction instead of starting another one.

This prevents a concurrent settings rewrite from re-enabling raw nodes during cutover.

The deployed Edge architecture has one Manager process. The in-process gate is backed by the journal's one-row-per-instance database constraint, so even two accidentally overlapping service objects cannot create two active migration transactions; the loser reads and returns the existing status.

Active, pending, committed, dirty, and manual journals return their existing status. A clean `rolled_back` journal whose checkpoint cleanup is complete may be atomically replaced by a new tx id for an explicit retry; audit history remains in the audit table. This is the only terminal state that starts a fresh migration without separate repair.

Public instance methods acquire the gate once and call internal runtime primitives with an unforgeable lease created by the gate. Migration, rollback, same-image recreation, and pending-start completion reuse that outer lease and never call another public gated method, preventing self-deadlock. A mismatched or fabricated lease is rejected.

The gate also evaluates persisted state on every write. `manual_required` permits only read-only diagnosis; `pending_start_verification` permits only the explicit start/final-verification operation. This policy remains effective after the in-memory lease map is lost on Manager restart.

## Search design

### Exact lookup

If input is a syntactically valid npm module name, each configured source is queried directly for its packument before using fuzzy search.

- A package is returned only when its selected version has `node-red.nodes` and keyword `node-red`.
- `@mqttsnet/thinglinks-edge-nodes` returns immediately even when npm search indexing lags.
- `@mqttsnet/thinglinks-node-red-common` is rejected as a node result because it has no `node-red` metadata.
- The first configured source wins for duplicate package names.
- If every configured source returns not-found for an otherwise valid name such as `thinglinks`, continue with fuzzy search.
- The first configured source that resolves the exact package is authoritative. If it is not a Node-RED node package, return no result and do not let a lower-priority source or fuzzy search reinterpret it.
- Authentication, timeout, or server failures remain source failures rather than being rewritten as not-found; healthy later sources continue in configured order. If no exact result is found and at least one source failed, report the source failure instead of silently falling through to fuzzy search.

### Fuzzy lookup

For non-exact input, query npm search with the user's plain text. Do not concatenate `keywords:node-red <query>` because the observed npm endpoint ignores the trailing user query in that form.

Filter returned objects locally:

- keyword list contains exact `node-red` case-insensitively;
- name, description, or keywords contain the user's normalized terms;
- results remain source-attributed and source-priority ordered;
- one failed source does not fail the whole search.

## Package seed and trust root

The first compatibility image keeps `packages/thinglinks-nodes` at `/app/nodes` solely so legacy instances can still be created/rebuilt and failed migrations can roll back. npm-mode instances never copy or load that compatibility bundle. Removing it is a separate fleet-wide cleanup after no legacy-mode instance remains.

The image build also generates `/app/npm-seed` from the exact Edge package spec using the existing dependency-closure packer. The seed contains the original npm tarballs for Edge and common, not repacked `node_modules` directories.

Build gates verify:

- package name and version;
- SHA-512 integrity against the fixed contract;
- Edge declares exactly common `0.0.1`;
- Edge declares exactly three node types;
- common has no `node-red` field;
- no missing dependency closure.

`seedFromDir` remains generic and does not auto-approve arbitrary seed packages. A separate platform bootstrap approves only the exact Edge package/version constant because it is part of the signed ThingLinks product baseline. Common is seeded but never approved.

The two fixed package/version records are protected trust-root objects: generic store APIs cannot overwrite or delete their tarballs, and generic catalogue APIs cannot change or revoke the exact Edge baseline approval. Manager startup and every platform install re-read the stored bytes, recompute integrity, validate the dependency/node metadata contract, and fail closed on drift. The private registry also re-verifies fixed package bytes on every packument/tarball response and serves the exact in-memory buffer it just verified; a filesystem change between install preflight and npm fetch therefore fails rather than serving changed bytes. Generic non-platform packages retain their normal lifecycle.

## New instance creation

New instances use npm mode from the start. Runtime mode is an explicit argument to `createInstance` and every create/rebuild/upgrade/rollback path; it is never inferred from rendered settings text:

1. Persist the new instance row with `node_runtime_mode=npm`.
2. Generate settings with strict platform package exclusions and current palette policy.
3. Do not copy `/app/nodes` or create raw platform files.
4. Create and start the Node-RED container with Manager and private registry environment variables.
5. Wait for the Admin API to become ready.
6. Install exact Edge `0.0.1` through Node-RED `POST /nodes`, which resolves common through the Manager registry.
7. Verify module/version/types/enabled/error state from the Admin API and verify `/data/package.json`, the lock file, and installed package metadata/integrity from the instance filesystem.
8. In one database transaction persist `node_runtime_mode=npm`, `platform_node_version=0.0.1`, `node_migration_state=committed`, and the audit record; only then return successful instance creation.

If readiness, installation, integrity, or module verification fails, creation compensation keeps the DB row traceable while it stops/removes the container, removes the network, removes the data directory, and verifies each resource is absent. Only after verified cleanup is the row deleted. Any cleanup failure retains the row as `manual_required`, stores only a redacted compensation summary, records an audit entry, and returns an explicit compensation error. No half-created instance is reported as successful and no orphan can become invisible by deleting its DB row first.

## Existing instance migration transaction

### Preflight

Before touching runtime state:

- acquire the instance operation gate;
- require exact Edge approval `0.0.1`;
- require Edge/common tarballs in NodeStore and verify both integrities;
- verify Edge dependency closure and common's non-node boundary;
- verify the seven legacy files are exactly the known canonical files with canonical hashes and that `/data/nodes` contains no extra user files;
- create the durable journal/checkpoint described above, including original running/stopped state, whether Edge was already staged, hashes of settings, flows, credentials, package manifest/lock, and current node inventory;
- verify container environment exactly matches the current normalized Manager URL, instance id, and private npm registry. Compare the in-memory ingest token with the decrypted DB token by constant-time digest comparison; never persist or log either value. Missing or wrong values call an explicit same-image/same-data recreation path that preserves image id/tag, ports, resource limits, data, runtime mode, and original running/stopped state. Failure restores the checkpoint or becomes `manual_required`;
- reject a conflicting third-party owner of any target type.

### Staging

With raw nodes still serving existing flows:

1. If the exact Edge `0.0.1` with matching Edge/common manifests and lock integrities was already present, set `staged_before=true`, skip `POST /nodes`, and verify that existing state. A different version, partial install, or integrity mismatch fails preflight rather than being silently overwritten.
2. Otherwise install exact Edge `0.0.1` through Node-RED Admin API and set `staged_before=false`.
3. Require module and version to be present on disk with matching lock integrity.
4. Accept `type_already_registered` only for the three expected node sets during this staging phase.
5. Do not report the npm package as active yet.

### Cutover

1. Render npm-mode settings with the three legacy JS basenames added to `nodesExcludes`.
2. Write settings and restart once if the instance was originally running.
3. Wait for the Admin API and flows to become ready.
4. If the instance was originally stopped, restore the checkpoint into a separate Manager-controlled probe root, start a uniquely named temporary container/network with the same immutable image id and reconstructed configuration, and perform install/cutover/verification against the copy. The verified probe exports only an allow-listed manifest for settings, package/lock, Node-RED module-state files, and exact Edge/common package directories; each entry records existence, kind, hash, and mode. The Manager prepares same-filesystem partial siblings only for entries that exist in the probe, fsyncs/hash-verifies them, and persists `cutover`. Apply all four states explicitly: both absent is a no-op; probe-only atomically renames partial to target; live-only atomically renames target to a tx backup as deletion; both present either equal-skip or backup-then-swap. Every mutation is fsynced and barrier-observable, and the code never overwrites a non-empty directory. A crash during the multi-file sequence is identified by the durable phase and always restores the immutable checkpoint; partials/backups are never treated as success. After final existence/hash/mode verification, state becomes `pending_start_verification`; the actual instance remains stopped. Its next explicit start performs live ownership/flow verification before the atomic `committed` transition. Probe resources use a separate sibling root and are removed/verified independently; failure rolls back and returns the production instance to stopped.

### Verification

Migration succeeds only when all assertions pass:

- module is exactly `@mqttsnet/thinglinks-edge-nodes`;
- version is exactly `0.0.1`;
- exactly three node sets exist and are enabled with no non-empty error;
- the three types are owned only by the npm module;
- the Admin API reports exactly the expected module/node sets; an optional observed `file` is retained as evidence but is not required by the API contract;
- `/data/package.json`, the lock file, and `/data/node_modules/@mqttsnet/thinglinks-edge-nodes/package.json` independently prove the exact npm package/version/integrity;
- raw entries are identified primarily by `module === "node-red"` plus a target `tl-*` type and no longer own any target type;
- all three Edge runtime node sets load healthy, which proves their top-level common dependency resolved; common itself does not appear in Node-RED inventory;
- flow and credentials hashes are unchanged;
- no unknown-node or duplicate-type startup errors exist;
- the existing flow remains readable/healthy; live migration does not deploy, replace, or later remove any synthetic test flow;
- Manager reporting failure is not part of module-ownership acceptance and does not invalidate a healthy module migration.

After verification, a single DB transaction writes npm mode, platform version, committed state, and the success audit record.

The five endpoint calls, 503 behavior, invalid configuration, and exact message passthrough are exercised only on isolated disposable data copies/acceptance instances. They are never injected into a user's live instance as a migration side effect. New-instance bootstrap relies on healthy loading of the three Edge runtimes (which import common) and leaves its initial flow/Manager ledger hashes unchanged before returning success; it does not require forbidden Docker exec access.

## Rollback

Rollback prioritizes restoring service:

1. If `staged_before=false` and the running Admin API is still safely reachable, attempt the official npm-package uninstall and record its cleanup result. Never uninstall a package that predated migration.
2. Stop the production container when needed. Restore checkpointed module state, package/lock, settings, flows, and credentials **after** any uninstall, then verify every final hash; an originally stopped instance is restored directly from the checkpoint without being started.
3. Render legacy mode without the three platform exclusions and restore the original running/stopped state.
4. For an originally running instance, verify the raw three types are again reported by module `node-red` and existing flows are healthy; for an originally stopped instance, verify on an isolated copy and leave the live instance stopped.
5. Keep DB runtime mode as `legacy`. An uninstall failure may yield `rolled_back_dirty` only after final checkpoint restoration and raw service verification succeed.

Outcomes:

- `rolled_back`: raw service restored and staged npm package removed cleanly.
- `rolled_back_dirty`: raw service restored but npm files or manifest entries remain.
- `manual_required`: raw service could not be restored; automation stops and provides exact recovery evidence.

The Manager never loops destructive retries automatically after `manual_required`.

## Inventory truth model

Node inventory preserves node-set evidence instead of flattening it away:

- module and version;
- types;
- enabled state;
- every non-empty error;
- optional observed file/path evidence when the Node-RED response supplies it;
- source: `builtin | raw | npm | mixed | unknown`;
- health: `healthy | conflict | failed`;
- compliance: `builtin | platform | approved | unapproved`.

Only the exact package `@mqttsnet/thinglinks-edge-nodes` is classified as a platform package. The whole `@mqttsnet` scope is not trusted because the organization publishes other products. Common never appears in inventory. Raw ownership is derived from `module === "node-red"` plus target types; npm filesystem ownership is verified separately rather than fabricated from an Admin API path field.

An install API response is successful only when the installed module is healthy. HTTP 200 with node-set errors is returned as failure with the original Node-RED evidence.

## HTTP and UI surface

Add explicit endpoints:

```text
GET  /api/instances/:id/nodes/thinglinks-migration
POST /api/instances/:id/nodes/thinglinks-migration
```

The POST requires instance operate permission and CSRF protection. It starts or returns the single migration transaction for that instance. `index.ts` constructs the migration service, `http/app.ts` adds it to `HttpContext`, and the catalogue route receives it through its explicit dependencies.

The Nodes page shows:

- direct Flow Library and Community catalogue links with wording that they are external discovery gates, not live status asserted by the Manager;
- exact/fuzzy source results;
- platform package cached/approved/installed/active status;
- migration phase and last error;
- node source and module health;
- an explicit migration action with downtime and rollback warning.

No approval, search, or page refresh silently starts migration or restarts an instance.

## Test strategy

### Unit tests

- exact package lookup bypasses stale search indexes;
- common exact lookup is rejected as a node package;
- fuzzy search uses plain query text and locally filters `node-red` packages;
- runtime-mode persistence and settings rendering;
- npm-mode legacy exclusions do not exclude npm node sets;
- inventory retains errors and detects duplicate ownership;
- platform classification trusts only the exact Edge package;
- every migration stage and rollback outcome, including process interruption at each non-terminal phase for both originally running and stopped instances;
- a second migration call is idempotent and concurrent operations are blocked.
- operation-gate coverage for install, whole-flow POST, start, stop, policy, credential, upgrade, remove, and reverse-proxy writes;
- runtime trust-root overwrite/delete/tamper attempts fail closed.

### Integration tests

- a real v12 database with existing rows upgrades to v13, preserves data, creates the journal schema, and remains idempotent on another startup;
- exact platform bootstrap approval does not approve arbitrary seeds;
- new-instance install and each cleanup failure produce either verified zero residuals or a traceable `manual_required` row;
- migration API permissions and CSRF;
- source failure isolation and source priority;
- package version/integrity and dependency closure gates.
- Manager startup awaits interrupted migration recovery before opening its listener.

### Real-container tests

Use `nodered/node-red:5.0.4-24-minimal` and the exact cached npm tarballs:

The verifier starts the real Manager image and drives instance creation and migration through Manager HTTP APIs. Node-RED Admin API, package files/locks, hashes, logs, and Docker inspection are supporting evidence only; direct edits cannot substitute for the product path.

Crash/failure phases use an object-injected verifier barrier at exact persisted/effect boundaries. The verifier launches the same image with a read-only alternate entry module and bind-mounted control directory; production `main()` receives a no-op barrier, and no environment variable, HTTP route, database flag, or UI control can activate fault injection.

1. New instance starts without copied raw nodes and loads Edge/common through Manager registry while external network is unavailable.
2. Existing running legacy data copy stages npm, cuts over, and preserves flows and credentials.
3. Existing stopped legacy data copy validates in an isolated probe, migrates its live data, and remains stopped.
4. Missing container environment exercises same-image/same-data recreation, including rollback on rebuild failure.
5. Injected failure and Manager termination at every non-terminal phase recover from the durable checkpoint for running and stopped instances.
6. New-instance install and compensation failure phases prove zero residuals or an explicit traceable `manual_required` state.
7. On a disposable verification copy, `allowList=[Edge]`, `denyList=["*"]` loads three types; common is absent from allowList and inventory.
8. Keeping the package installed but applying a verifier-only settings override that removes Edge from allowList makes all three types disappear after restart while raw remains excluded.
9. Restoring the disposable copy's allowList makes all three types reappear and the flow execute again. This test never revokes or mutates the protected product baseline approval and exposes no production policy-bypass API.
10. The real Manager receives the five Edge endpoints, derives instance from token, and ignores any body-level instance impersonation.

### Browser and external gates

- Flow Library detail and search pages contain the package.
- The official Community catalogue must contain the package before claiming Palette Manager official-directory discovery.
- A fresh Node-RED 5.0.4 editor selecting the Node-RED Community catalogue must find the package by `thinglinks`; a Flow Library page alone does not satisfy this gate.
- ThingLinks catalogue shows approved Edge immediately and never shows common.
- Browser console and catalogue requests are error-free.

1. Search exact/fuzzy behavior and tests.
2. Platform package constants and runtime protection.

## Release and claim boundaries

Completion is reported in layers:

- **Code complete:** unit/integration tests and static checks pass.
- **Artifact complete:** exact Edge/common seed tarballs and integrities are verified.
- **Container complete:** new-instance, migration, rollback, allowList, and Manager matrices pass.
- **Local Edge complete:** isolated Edge-managed instance passes UI and runtime acceptance.
- **Existing instance complete:** `line-1` migrates only after separate user authorization and post-migration verification.
- **Official discovery complete:** Flow Library and official Community catalogue both expose the package; one cannot substitute for the other.
